# 测试驱动开发规则

`.claude/rules/workflow.md` §6 引用本文件。工作流规定「怎么拆任务、怎么提交」，本文件规定
「切片内部怎么用测试驱动实现」。两者的共同前提是垂直切片：一个切片交付一个可观察行为，
并包含验证该行为的测试。

一个人开发、没有 Review，测试是唯一能让你半年后敢动这段代码的东西。它的价值不在覆盖率
数字，而在于**重构时它还活着**。

## 1. 核心立场

**测行为，不测实现。** 好测试读起来像规格：「供应商超时后未使用的预留积分被释放」。它走真实
代码路径、只碰公开接口、重命名内部函数不会让它变红。一旦开始 mock 内部协作者、断言内部调用
次数、或绕过接口直接查数据库验证结果，就是在测实现，重构必炸。

**垂直推进，不横切。** 一个测试 → 一段实现 → 重复。禁止「先写 test 1–5 再写 impl 1–5」。
批量写出来的测试测的是想象中的行为，会在行为真的坏掉时通过、在行为没问题时失败。写完一段
实现你才真正知道下一个该测什么。

**绿之前不重构。** 红着的时候只做一件事：写最少的代码让它变绿。重构只在全绿后开始，且每步
重构后立刻重跑测试。红着重构会让你分不清是重构错了还是实现还没写完。

**只写当前测试需要的代码。** 不为未来的测试预埋功能，不加投机的抽象。

## 2. 循环的硬规则

- **必须先看到红，且红得有道理** —— 报的是缺失的行为，而不是语法错或导入失败。没见过红就
  写实现，等于没验证这个测试真的在测东西。
- 发现自己在连写第二个测试而上一个还没绿，**停下**。
- 不为「还没确认重要」的行为写测试。先想清楚这个行为值不值得钉，再写。
- 长期挡回归的测试必须落进 runner 能跑到的位置，不留在临时脚本里。一次性验证脚本用完即弃。
- 测试名用本项目领域词汇：Series、Episode、Scene、Shot Version、Generation Run、
  Generation Task、Credit Ledger、Provider Adapter。不要 `test_works`、`shouldWork`。

## 3. 必须测试先行的部分

以下改动**不接受「先实现、后补测试」**。它们的共同点是：错了不会立刻报错，但会造成真实
损失，且事后很难从日志倒推。

| 领域 | 必须先钉住的行为 |
|---|---|
| 积分账本 | `Estimate → Reserve → Execute → Settle` 全路径；可用与预留不得为负；同一任务不重复预留或结算；account 汇总等于 ledger 聚合；失败释放；取消只结算已完成部分 |
| 状态机 | Episode、Generation Run、Generation Task 的合法与非法迁移；非法迁移必须被拒绝而不是静默通过 |
| 幂等 | 相同 `Idempotency-Key` 的重复写请求返回同一业务结果；任务幂等键 `run + operation + target + version` 吸收重复投递；`provider + event_id` 去重 |
| Workspace 隔离 | 跨 Workspace 读写一律拒绝；列表接口不泄漏他人数据 |
| 乐观锁 | Revision 冲突返回明确冲突响应，不覆盖他人改动 |
| Outbox | 业务事务与 Outbox Event 同生共死；事务回滚后队列里不留幽灵任务 |

交付策略（`docs/implementation-plan.md` §4）已经把「新增付费操作有积分不变量测试」列为阶段
准入条件。上表是它的展开。

## 4. 不适合 TDD 的部分

诚实划清边界，比假装什么都能 TDD 更有用：

- **成片观感与角色一致性。** 这是人工评分（`docs/ai-comic-drama-saas-design.md` §34.3 的五
  维度评分表），不是断言。自动化只能钉住可测量的部分：FFprobe 读出的分辨率、帧率、编码、
  时长，以及片段数量与时间线对齐。
- **模型输出质量。** 测的是「拿到结构化结果后系统怎么处理」，不是「模型返回得好不好」。
- **视觉呈现。** 走 Light / Dark 视觉回归快照，属于验证而非驱动。
- **探索性原型。** 还在试手感的代码不必 TDD，但一旦决定保留就要补上行为测试，并把原型丢掉。

## 5. 测试层次

来自 `docs/ai-comic-drama-saas-design.md` §16.2、§31.1 与实施计划各阶段完成标准。

| 层次 | 范围 | 工具 |
|---|---|---|
| Domain 单元 | 状态机、镜头版本规则、费用计算、账本不变量、幂等键生成。纯函数，不碰数据库和框架 | Vitest |
| API 集成 | Better Auth、Workspace 隔离、乐观锁、幂等接口、签名上传、Outbox 写入、Cursor 分页 | Vitest + Hono `testClient()` |
| Worker | 重试与退避、超时、取消、回调乱序、重复回调、积分补偿、优雅停机 | Vitest |
| Provider 契约 | 所有适配器必须通过**同一套**契约测试套件 | Vitest |
| 组件 | 向导校验、任务状态、警告、镜头检查器、表单 `data-invalid` / `aria-invalid` | Vitest + Testing Library |
| E2E | 注册 → 购买积分 → 创建系列 → 生成单集 → 局部重做 → 导出 | Playwright |
| 故障注入 | Redis 暂时不可用、供应商超时、数据库提交失败、上传成功但数据库回写失败 | Vitest / Playwright |
| 无障碍 | 键盘流程、焦点可见性、标签、对比度 | Playwright |
| 视觉回归 | 核心组件与关键页面的 Light 与 Dark，桌面与小屏两档 | Playwright `toHaveScreenshot` |

API 路由测试用 Hono `testClient()`，它同时验证运行行为和 RPC 类型推导 —— 类型推导错误在这
一层暴露，比在 Web 里发现便宜得多。

视觉回归用 Playwright 自带的 `toHaveScreenshot`，不引第三方快照服务：E2E 与无障碍已经在
Playwright 上，同一个 runner、同一次构建就能出快照，不值得再养一套上传比对的基础设施。

它唯一容易失控的地方是跨平台渲染差异，所以这里只有一条规则：**基线只有一份，属于钉住的
`mcr.microsoft.com/playwright:v<版本>-noble` 容器。** 镜像 Tag 由已安装的 `@playwright/test`
版本推导（`e2e/visual.sh`），不会出现「依赖升了、Tag 没升」这种比错渲染器的情况。本地和 CI
都通过 `pnpm test:e2e:visual` 在同一个镜像里跑，因此 PR 里的比较结果本地可以逐字复现。开发机
上顺手跑出的 `-darwin` / `-win32` 快照被 `.gitignore` 挡住，不会变成第二份权威；在非 Linux 上
直接跑视觉项目会报错并指向正确命令。容差 `maxDiffPixelRatio: 0.002` 只吸收字体栅格化的抖动，
颜色、圆角、间距的改动都是上千像素级别，挡不住。

更新基线：`pnpm test:e2e:visual --update-snapshots`，然后**逐张看过再提交**。这一层是验证而不
是驱动（§4），把一张错的渲染钉成基线比没有基线更糟。`pnpm test:e2e` 不含视觉回归，一次命令跑完
行为与无障碍两层。

它需要 PostgreSQL（`pnpm docker:up`）：Playwright 自己在 3101 起 API、3100 起 Web，因此这一层
测的是真实链路 —— 浏览器打自己的源、Next 转发 `/api/*`、Better Auth 下第一方 Cookie、后续业务
请求被认出来。这条链上每一环都是配置，而配置不会在单元测试里出错，只会在生产里。需要会话的
页面从 `e2e/support/session.ts` 注册一个真账号，不注入 Cookie。

## 6. 本项目的测试硬约束

**CI 绝不调用真实付费生成。** 所有工作流测试走 Fake Provider。真实供应商调用只出现在 F-00
的一次性实验脚本和人工冒烟测试里。一个会烧钱的 CI 会在第一次意外重跑时教育你。

**断言走公开接口，但账本必须被验证。** 这两条看似冲突，解法是：验证积分行为时断言 Credit
Balance 与 Ledger 查询接口的返回，而不是直接 SQL 查 `credit_ledger_entry` 表。账本是领域
概念、有对外查询接口，不是实现细节；表结构是实现细节。

**mock 只在系统真实边界处。** 真实边界是：模型供应商 HTTP、Stripe、对象存储、邮件。
PostgreSQL 和 Redis 不是边界 —— 用 Docker Compose 起真实实例，事务和约束行为本身就是被测
对象的一部分（`docs/implementation-plan.md` §2 明确：不得用 Zod 校验替代数据库完整性约束，
所以那些约束必须被真实数据库验证过）。

**Zod 契约先于测试。** 新增外部输入的顺序是：定义 Zod Schema → `z.infer` 推导类型 → 写测试
→ 实现。测试直接消费 `packages/contracts` 的 Schema，不在测试里手写重复的结构。

**测试数据用工厂，不用共享 fixture。** 工厂放 `packages/testkit`。每个测试自己造需要的数据
并带上 Workspace 归属，避免测试之间通过共享状态耦合。

## 7. 难测的部分怎么下手

- **供应商回调乱序 / 重复。** 不要试图模拟真实时序。把回调处理写成纯函数（当前状态 + 事件
  → 新状态或拒绝），然后直接按任意顺序喂事件序列。乱序测试退化成表驱动的单元测试。
- **长任务恢复。** 不要等真实任务跑完。测的是「给定数据库里这样一个 Generation Task 状态，
  Worker 重启后做什么」—— 构造中间状态，跑 Reconciler，断言结果。
- **SSE 断线重连。** 测游标语义：带 cursor 重连后不重复、不丢事件。不测 socket 本身。
- **FFmpeg 合成。** 用极短的固定测试素材（秒级），断言 FFprobe 读出的输出参数和分段数量，
  不断言画面内容。

## 8. 每颗追踪弹的收尾自查

```text
□ 测试描述的是行为，不是实现？
□ 只用了公开接口？
□ 内部重构后这个测试还会活着？
□ 实现是通过这个测试所需的最小量？
□ 有没有偷加投机功能？
□ 见到过红，且红在缺失行为上？
```

全绿后再看重构机会：去重、把复杂度移到更小的接口背后。每步重构后重跑测试。

## 9. 运行

命令随 F-01 建立，届时以 `package.json` 实际内容为准。规划中：

```bash
pnpm --filter <workspace> test                          # 开发中优先跑受影响 workspace
pnpm --filter <workspace> test -- path/to/file.test.ts  # 单文件
pnpm --filter <workspace> test -- -t "测试名称"          # 单用例
pnpm test                                               # 提交 PR 前
```

涉及数据库或完整用户流程时追加 `test:integration` 与 `test:e2e`。
