# ADR-008 任务载荷版本与 Worker 滚动升级策略

- 选了什么：BullMQ 任务载荷由带判别字段的 Zod Schema 定义并携带 Schema Version，生产者与消费者两端都校验。发布时先部署兼容旧载荷的 Worker，再逐步投递新版本载荷。数据库迁移由独立发布任务执行，破坏性变更走 Expand → Migrate → Contract。

- 否掉了什么 / 为什么：
  - **无版本号的裸载荷**。滚动升级期间新旧 Worker 必然同时消费同一队列，旧 Worker 遇到新字段会静默出错或崩溃，队列里的存量任务在新 Worker 上又可能解析失败。失败的还是用户已经预留了积分的任务。
  - **停机升级、清空队列后上线**。单集生成是分钟级甚至更久的任务图，清队列等于丢弃用户已付费的在途工作。
  - **每次载荷变更就换队列名**。队列数量随迭代膨胀，旧队列里的残留任务无人消费，等于把问题从"解析失败"换成"永远排队"。

- 当时的前提：任务生命周期长，发布期间队列里必然有在途任务；用户已为这些任务预留积分；PostgreSQL 是任务真相所在，队列可重建（见 ADR-002、ADR-003）。

- 已知代价：每次载荷变更要保留一个版本的兼容期与兼容代码，且需要主动清理，否则会长期堆积；发布从一步变成两步。

- 何时重审：任务典型时长缩短到可以安全排空队列；或引入 Schema Registry 之类的统一版本机制。
